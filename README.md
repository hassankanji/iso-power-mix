# U.S. ISO Generation Mix Tracker

Daily electricity generation-by-fuel-type data pulled directly from the 7 major U.S. ISOs/RTOs, normalized into a shared schema, stored in DuckDB, and visualized in a static dashboard.

**ISOs covered:** CAISO, PJM, ERCOT, MISO, SPP, NYISO, ISO-NE
**Fuel buckets:** `natural_gas`, `coal`, `nuclear`, `hydro`, `wind`, `solar`, `other_renewables`, `storage`, `imports_other`

## Repo structure

```
iso-power-mix/
├── src/
│   ├── connectors/        one module per ISO (caiso.py, pjm.py, ercot.py, miso.py, spp.py, nyiso.py, isone.py)
│   ├── db.py               DuckDB schema + idempotent upsert
│   ├── pipeline.py          orchestrator: backfill on first run, incremental after, per-ISO failure isolation
│   ├── export.py            exports the DB to docs/data/*.json for the dashboard
│   └── schema.py            canonical fuel categories / column names
├── scripts/run_pipeline.py  CLI entrypoint
├── data/power_mix.duckdb    the database (committed to the repo)
├── docs/                    static dashboard, served via GitHub Pages
│   ├── index.html, app.js, style.css
│   └── data/*.json          generated by src/export.py, consumed by the dashboard
└── .github/workflows/daily.yml   daily automation
```

## Per-ISO research findings

| ISO | Auth required | Source | Format | Interval | Reliable history |
|---|---|---|---|---|---|
| **CAISO** | No | `caiso.com/outlook/history/{date}/fuelsource.csv` (not the OASIS API — OASIS doesn't cleanly expose actual fuel-mix history) | CSV | 5-min | 2019-01-01 → present (earlier dates 404) |
| **ERCOT** | No | `ercot.com/gridinfo/generation` — annual XLSX + `FuelMixReport_PreviousYears.zip` (2007–2024 archive) | XLSX | 15-min | 2007-01-01 → present |
| **SPP** | No | `portal.spp.org` file-browser API — `GenMix_{year}.csv` annual archives, `GenMix365_SPP.csv` rolling file for the current year | CSV | 5-min | 2011-01-01 → present |
| **NYISO** | No | `mis.nyiso.com` — monthly zip archives + loose daily CSVs (P-63 report) | CSV | 5-min | 2015-12-09 → present |
| **PJM** | **Yes** | `api.pjm.com` Data Miner 2, `gen_by_fuel` feed | JSON | hourly | Conservatively set to 2015-01-01; PJM does not document an official cutoff for this feed |
| **MISO** | **Yes**, for history; no-auth path exists for today/yesterday | `public-api.misoenergy.org` (today/yesterday, no auth) + `data-exchange.misoenergy.org` LGI API (historical, registered) | JSON | ~5-min | See **MISO limitation** below — true backfill is not reliably available |
| **ISO-NE** | **Yes** | `webservices.iso-ne.com` Web Services API, `genfuelmix/day/{date}` | JSON/XML | sub-hourly | 2008-01-01 → present |

Daily MWh is computed as `mean(MW across that day's readings) × 24` for every connector — this is robust to each ISO's native sampling interval and tolerates small gaps, rather than assuming a fixed interval length.

### Known limitations (read before trusting the numbers)

- **MISO**: its legacy public "Historical Generation Fuel Mix" reports were discontinued December 12, 2025. The no-auth `FuelMix/Today` and `FuelMix/Yesterday` endpoints work but only cover the current and prior day, and MISO's own "yesterday" data is sometimes sparse (observed days where only the `Imports` category was populated). MISO's "Other" category also folds in Hydro, Pumped Storage, Diesel, and Demand Response — there's no way to break hydro out separately from this feed. Real historical backfill requires a MISO Data Exchange (LGI API) key; the exact resource path for that is a best-effort implementation in `src/connectors/miso.py` and is **unverified** — it degrades gracefully (skips and logs a warning) if wrong, rather than crashing.
- **PJM**: the exact `fuel_type` string values returned by `gen_by_fuel` were not confirmed against a live response (no API key available while building this). The mapping in `src/connectors/pjm.py` is built from PJM's publicly known dashboard categories plus values seen in an open-source PJM client, with any unrecognized value safely bucketed into `imports_other` rather than dropped. Recommend spot-checking after you have a real key.
- **ISO-NE**: connector is written to spec and its error-handling paths are verified, but actual data fetching is untested (no ISO Express credentials available while building this). Recommend a smoke test against a known date once you've registered.
- **ERCOT**: no dedicated battery/storage column exists in ERCOT's report through 2026; storage will simply show no ERCOT rows.
- **NYISO**: "Dual Fuel" (plants that can burn either oil or gas) is bucketed into `natural_gas` as a simplification.
- **SPP**: timestamps are GMT and used as-is for the `date` column (not converted to local time) — a day boundary may be a few hours off from other ISOs' local-time day boundaries.

## API registration — do this before the pipeline can pull PJM, MISO, or ISO-NE data

CAISO, ERCOT, SPP, and NYISO need **no registration** — they work out of the box.

### PJM
1. Go to https://apiportal.pjm.com/ and sign up (or via https://accountmanager.pjm.com/accountmanager/pages/public/new-user.jsf).
2. Verify your email (the verification link expires in 4 hours).
3. If you're not part of a PJM member company, email `accountmanager@pjm.com` confirming the key is for internal, non-commercial use.
4. Once approved, log into apiportal.pjm.com → **Profile → Subscriptions** and copy your Primary subscription key.
5. Put it in `.env` as `PJM_SUBSCRIPTION_KEY=...`.
   Note: non-member accounts are rate-limited to ~6 requests/minute — the connector already paces itself accordingly.

### MISO
1. Go to https://data-exchange.misoenergy.org/ and create a free account.
2. Subscribe to the Load, Generation & Interchange (LGI) API family from the portal.
3. Put your key in `.env` as `MISO_API_KEY=...`.
   Note: the pipeline works without this key too (it'll just be limited to the last 2 days of data per run instead of full history) — see the MISO limitation above.

### ISO-NE
1. Go to https://www.iso-ne.com/ and create a free ISO Express account (linked from `https://www.iso-ne.com/participate/support/web-services-data`).
2. This account's username/password work directly as HTTP Basic Auth credentials for the Web Services API — no separate approval step.
3. Put them in `.env` as `ISONE_USERNAME=...` and `ISONE_PASSWORD=...`.

## Running locally

```bash
cd iso-power-mix
python -m venv venv
venv\Scripts\activate          # Windows
pip install -r requirements.txt
copy .env.example .env         # then fill in PJM/MISO/ISO-NE credentials if you have them
```

Run the pipeline:

```bash
# Incremental / first-run backfill for every ISO (auto-detects: backfills from each
# connector's earliest reliable date if that ISO has no data yet, otherwise pulls
# from the last stored date forward)
python scripts/run_pipeline.py

# Just a couple of ISOs, useful for testing
python scripts/run_pipeline.py --iso CAISO,ERCOT

# Force a specific date range (e.g. re-backfill a range)
python scripts/run_pipeline.py --start 2020-01-01 --end 2020-12-31
```

Each run upserts into `data/power_mix.duckdb` (safe to re-run — it replaces rows for the same date/ISO/fuel_category rather than duplicating) and regenerates `docs/data/*.json` for the dashboard. One ISO failing (bad credentials, source outage, etc.) is logged to the `ingestion_log` table and printed as a warning — it never stops the other 6 ISOs from running.

## Automation (GitHub Actions)

`.github/workflows/daily.yml` runs once a day at 13:00 UTC (and on manual trigger), pulls the prior day's data for all 7 ISOs, and commits the updated `data/power_mix.duckdb` + `docs/data/*.json` back to the repo. A single ISO failure produces a `::warning::` annotation on the run but doesn't block committing whatever data did succeed.

**Required GitHub Actions secrets** (Settings → Secrets and variables → Actions), only needed for the 3 ISOs that require auth:
- `PJM_SUBSCRIPTION_KEY`
- `MISO_API_KEY` (optional — pipeline degrades gracefully without it, see MISO limitation)
- `ISONE_USERNAME`, `ISONE_PASSWORD`

The workflow needs `contents: write` permission (already set) to push commits back to the repo using the default `GITHUB_TOKEN`.

The very first run will backfill full history per ISO and can take significantly longer than the routine daily incremental pull (job timeout is set to 300 minutes to accommodate this).

## Dashboard

Static site in `docs/`, reads directly from the committed `docs/data/*.json` files — no backend required.

**View locally:**
```bash
cd docs
python -m http.server 8420
# open http://localhost:8420
```

**Deploy:** enable GitHub Pages in repo Settings → Pages → "Deploy from a branch" → branch `main`, folder `/docs`. The dashboard updates automatically every time the daily workflow commits new data.

Three views: national mix over time (stacked area, date-range filterable), per-ISO breakdown (selectable ISO + date range), and a latest-snapshot view showing each ISO's most recent available day plus a data-freshness table (flags any ISO more than 3 days stale).

**Scaling note:** `docs/data/iso_daily.json` is the full per-ISO-per-day-per-category grain and already reaches ~14MB after backfilling CAISO/ERCOT/SPP/NYISO history (GitHub Pages gzips this in transit, so actual download is much smaller). It will keep growing slowly (~7 ISOs × 9 categories × 1 row/day). If it becomes unwieldy, the straightforward next step is splitting it by year or switching to a binary format (Parquet) loaded with a small WASM reader instead of one flat JSON file.
